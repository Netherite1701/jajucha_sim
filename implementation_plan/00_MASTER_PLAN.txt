Jajucha Simulator v2 — Master Engineering Prompt
You are the primary engineering agent responsible for implementing Jajucha Simulator v2, a clean Unity-based simulator for the Jajucha autonomous-driving vehicle.
This is a fresh implementation. Do not attempt to salvage or incrementally repair the old simulator architecture. Previous implementations may be inspected for lessons or requirements, but they are not architectural authority.
Your job is to build a deterministic, maintainable simulator that closely reproduces the real Jajucha programming interface and competition environment while also providing a powerful runtime map editor, competition scoring system, debugging tools, and automated testing.

1. Highest-Priority Rule: The Manual Is Ground Truth
The official Jajucha manual is the primary source of truth for all real-vehicle behavior and APIs.
The manual is available in the project/reference files as:
자주차 매뉴얼.pdf
Whenever there is any uncertainty regarding:

Authority order:

Never override the manual because an alternative implementation seems cleaner.
If the manual contradicts existing simulator code:

4. Design Decision Log
Every meaningful architectural decision must be recorded in:
docs/DESIGN_DECISIONS.md
Use ADR-like entries.
Example:
## DD-014 — Use one shared tile grid for course features

Status: Accepted

Context:
Roads, tunnels, ramps, signs, obstacles, and triggers need consistent placement and runtime editing.

Decision:
All course features use the same fixed-size tile coordinate system.

Consequences:
- simple runtime snapping
- consistent serialization
- structures can overlap road tiles using layers
- course editing works identically in Editor and standalone build

Alternatives considered:
- spline-only roads
- independent structure snapping systems
- Unity SceneView placement

Reason rejected:
They complicate runtime editing and create inconsistent coordinate systems.

Never silently make major architectural changes.
If a previous accepted decision must change:
document why,
mark the old decision superseded,
document the replacement,
update affected architecture documentation.

6. Permanent World Scale
The simulator uses:
1 Unity unit = 1 centimeter

Therefore:
1 m = 100 Unity units
gravity = 981 cm/s²

Default gravity:
Physics.gravity = new Vector3(0f, -981f, 0f);

All course dimensions, vehicle geometry, sensor positions, structures, speed calculations, and editor measurements should use centimeters unless explicitly documented otherwise.
Vehicle prefab root scale:
(1,1,1)

Never compensate for incorrect geometry using arbitrary Transform scaling.

9. Real-Compatible Jajucha Control API
The real Python library is:
jchm

not jhcm.
The simulator must support the real-style interface defined by the manual.
Known motor API:
jchm.control.set_motor(left, right, speed)

Respect manual-defined parameter ranges and semantics.
Do not redesign the API because another control interface would be easier.
Simulator-only functionality belongs in:
jchm_sim

Examples:
jchm_sim.reset()
jchm_sim.start()
jchm_sim.pause()
jchm_sim.step()
jchm_sim.get_result()

Never pollute jchm with simulator-only functions.

10. Vehicle
The simulated vehicle should reproduce the actual Jajucha control model rather than becoming a generic automotive simulator.
Known architectural requirements include:
front-wheel steering
rear-wheel propulsion
independent left/right front steering commands
speed controls propulsion
steering alone never creates propulsion
Hard invariant:
speed == 0
→ propulsion force == 0

The front wheels may steer while stationary, but the vehicle must not intentionally move because steering changed.
Do not average left/right steering commands.
Do not impose generic Ackermann behavior if doing so overrides real jchm semantics.
Prefer a controlled custom vehicle/contact implementation over blindly relying on WheelCollider if it causes instability.

11. Bridge
Python communicates with Unity through a versioned localhost bridge.
Default concept:
127.0.0.1:8765

The networking thread must never directly access Unity objects.
Correct pattern:
network thread
    ↓

    ↓
simulation/main thread
    ↓
Unity systems

Include:
protocol versioning
request IDs
validation
clear errors
reconnect behavior

safe disconnect behavior
Disconnect/watchdog must stop propulsion.

12. Cameras
The real Jajucha camera system described by the manual is the authority.
Support the real-facing APIs such as:
jchm.camera.get_image("left")
jchm.camera.get_image("center")
jchm.camera.get_image("right")
jchm.camera.get_depth()
jchm.camera.show_image(...)

Implement separate physical Unity cameras for left, center, and right.
Do not simulate them by cropping one wide camera.
Python-visible images should match the manual/OpenCV usage.
Camera capture rate must be independent from simulation tick rate.
get_image() should normally return the latest sensor frame rather than forcing a new render every call.

13. Depth

The simulator may internally retain metric ground-truth depth.
However:
do not expose metric depth through jchm.camera.get_depth() if the real API returns grayscale depth.
Simulator-only diagnostic APIs may expose extra ground truth separately.

17. Shared Tile Grid
The course uses one shared fixed-size tile grid.
Roads and structures use the same tile dimensions and same coordinates.
Conceptually:
CourseGrid
├─ Road Layer
├─ Structure Layer
├─ Object Layer
└─ Trigger Layer

Layers may overlap.
Example:
Tile (10,12)

Road:
Road

Structure:
Tunnel

Trigger:
SlowZone

A tunnel therefore sits over existing road tiles rather than replacing the road data.
Tile size must be configurable and stored in physical centimeters.
All placement and snapping must use this same grid system.

24. Competition Speed Measurement
Match the real competition method.
Speed is measured using two physical/logical terminals.
Terminal A              Terminal B
    │                        │
    │<-------- d ----------->│
   t1                       t2

Official measured speed:
v = d / (t2 - t1)

Use simulation-time timestamps.
Do not use instantaneous Rigidbody velocity as the official competition speed result.
A terminal pair must reset completely between runs.
Unless otherwise configured:
A → B

is valid and reverse order is ignored.

26. Line Contact
Touching/stepping on a forbidden course line should produce a scoring violation.
Do not test only the vehicle center.
Evaluate an appropriate vehicle footprint or contact geometry.
Debounce continuous contact:
not touching
→ touching
= one violation

remain touching
= same violation

leave
→ episode ends

Do not deduct points every simulation tick.

49. When Something Is Unclear
Do not guess silently.
Use this procedure:
1. Check Jajucha manual.
2. Check existing design documentation.
3. Check configuration/calibration records.
4. If still unknown, choose a conservative configurable implementation.
5. Mark it APPROXIMATE or UNKNOWN.
6. Document why.
7. Continue implementation without pretending certainty.

Do not block the entire project merely because a hardware value is unknown if it can safely remain configurable.

50. Definition of Project Success
The simulator is successful when:
real-style jchm programs can run against it with minimal/no simulator-specific changes,
the physical model is stable enough for autonomous-driving development,
cameras and depth behave consistently with the documented real API,
courses can be built and edited from the standalone application,
road, structures, objects, and triggers share a common tile grid,
real course drawings can be converted into editable simulator maps,
tunnels, ramps, signs, obstacles, triggers, and speed terminals can be placed at runtime,
competition objectives and negative-point scoring can be configured,
two-terminal d/(t2-t1) speed measurement is supported,
repeated runs reset cleanly,
testing is independent of the user's autonomous-driving architecture,
runs can be automatically scored and repeated,
failures can be reproduced,
the Jajucha remains visible while driving,
debug tools work in standalone builds,
student sensor images never contain simulator-only ground truth,
documentation accurately explains both implementation and design rationale.

Final Rule
When forced to choose between:
something convenient for the simulator

and:
something faithful to the actual Jajucha/manual
