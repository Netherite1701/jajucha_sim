Yes — then Step 10 should not be “testing only.” It should be a combined Competition Evaluation System: scoring + batch testing + reproducible runs.
Step 10 — Competition Scoring + Automated Testing
The simulator should evaluate a run the way a competition judge would.
Core flow:
Reset
  ↓
Start
  ↓
Drive course
  ↓
Detect penalties / objective failures / terminal speed
  ↓
Finish or timeout
  ↓
Calculate final score
  ↓
Save result
  ↓
Optionally repeat automatically

1. Scoring model
Use:
Final Score
=
Base Score
- Penalties

I would not hardcode the actual penalty values yet unless you provide the real rules.
Instead define configurable rules like:
Line contact             -X points
Obstacle collision       -X points
Objective failure        -X points
Speed violation          -X points
False start              -X points
Course departure         -X points
Timeout                  -X points

That way the simulator can exactly match the competition rules later.

2. Line stepping / line contact
This should be a real scoring event.
The road tile system should distinguish:
Road surface
Boundary line

Then detect if the Jajucha footprint touches/crosses the forbidden line.
Do not just check the car's center.
Use several contact/footprint points, for example:
front-left
front-right
rear-left
rear-right

or the actual chassis/wheel footprint.
Conceptually:
car footprint
      ↓
boundary-line geometry
      ↓
overlap?
      ↓
LineViolation
      ↓
penalty

Example event:
18.42 s
LINE_CONTACT
section: curve_02
penalty: -5

The number -5 is only an example; actual scoring stays configurable.

3. Don't deduct every simulation tick
If the car stays on the line for 0.5 seconds, don't generate:
50 penalties

Use a violation episode:
not touching
→ touching
= one LineViolation

remain touching
= same violation

leave line
→ episode ends

If it later touches again:
new violation

This same debouncing principle should apply to collisions.

4. Objective system
Each important course feature can define an objective.
Examples:
Pass tunnel successfully
Complete obstacle section
Obey slow section
Pass speed measurement section
Recognize/start after signal
Reach finish

The scorer doesn't care how your code accomplishes them.
Each objective has:
ID
success condition
failure condition
penalty
optional timeout


5. Objective states
Use:
Pending
Passed
Failed
Skipped

Example:
objective_tunnel_01
Pending
   ↓ car enters
Active
   ↓ exits correctly
Passed

or:
enters tunnel
↓
hits tunnel wall / exits forbidden side
↓
Failed
↓
penalty

7. Objective regions use the same tile grid
Since the entire course uses the common tile grid, an objective can reference:

Example:
{
  "id": "tunnel_objective_01",

Simple.

8. Course departure
Road tiles give us a very clean way to detect this.
Sample the car footprint.
If too much of it is outside:
Road Layer

then generate:
COURSE_DEPARTURE

This can either:
deduct points

or, for severe departures:
fail objective / terminate run

depending on rules.

9. Collision scoring
Collisions should identify what was hit.
For example:
Obstacle
Tunnel wall
Barrier
Other structure

Result:
31.24 s
COLLISION
object: obstacle_02
penalty: -5

Again:
continuous contact = one incident

not one penalty per physics callback.

10. Start-signal scoring
Possible scoring events:
false start
failed to start
valid start

Example:
signal RED
car crosses start line
→ FALSE_START
→ penalty

The autonomous program still gets no hidden signal state.
It must see the actual visual start signal.

11. Slow-zone scoring
For competition realism, we should distinguish:
Zone behavior
Whether the objective was completed correctly.
Terminal measured speed
Actual official measured speed:
\[ v=\frac{d}{t_2-t_1} \]
So the scorer can say:
Speed objective:
Terminal A: 24.100 s
Terminal B: 25.020 s
Distance: 20 cm

Measured:
21.74 cm/s

Limit:
20 cm/s

FAIL
Penalty: -X

Do not use instantaneous Rigidbody speed as the official measurement.

12. Terminal pair as a scoring device
Data:
SpeedTerminalPair
├─ Terminal A
├─ Terminal B
├─ distance
├─ allowed threshold
└─ scoring rule

When A then B is crossed:
Δt = t2 - t1
speed = d / Δt

Then scorer evaluates it.

13. Missing terminal measurement
Possible case:
A crossed
B never crossed

Then objective can become:
FAILED

at:
finish, or
objective timeout
depending on configuration.
This should not silently disappear from results.

14. Finish scoring
When finish is reached:
stop official timer
finalize unfinished objectives
finalize penalties
calculate score
create RunResult
Example:
RUN COMPLETE

Time             58.41 s

Base Score       100

Penalties:
Line contact      -5
Tunnel failure   -10
Collision         -5

Final Score       80

The actual base score and deduction values stay configurable.

15. Timeout
If:
elapsed > MaxRunTime

then:
TIMEOUT

Possible behavior:
unfinished objectives → fail
timeout penalty → apply
run ends

This should be scenario-configurable.

16. Penalty record
Every deduction should create a structured record:
PenaltyRecord
├─ RuleId
├─ EventType
├─ Points
├─ SimulationTime
├─ TargetId
└─ Description

Example:
{
  "eventType": "line_contact",
  "points": -5,
  "time": 18.42,
  "targetId": "road_boundary_03"
}

This makes results auditable.

17. ScoreManager
Keep scoring centralized:
Scenario events
     ↓
ScoreManager
     ↓
Rules
     ↓
PenaltyRecords
     ↓
FinalScore

Do not let every obstacle directly modify a global integer.
Bad:
score -= 5;

Better:
publish CollisionEvent
↓
CollisionRule evaluates
↓
PenaltyRecord created

This makes rules replaceable.

    "collisionPenalty": 5,
    "falseStartPenalty": 10,

19. Per-object override
Some objectives may have different penalties.
Example:

24. Now combine testing and scoring
TestRunner doesn't invent a separate scoring model.
It simply runs scenarios and collects their official RunResult.
Architecture:
              Scenario
                  │
                  ▼
             ScoreManager
                  │
                  ▼
              RunResult
                  │
          ┌───────┴────────┐
          ▼                ▼
    Results Panel      TestRunner
                           │
                           ▼
                      BatchRunner

So manual runs and automated tests use exactly the same scoring system.
This is important.

27. Batch success criteria
A test can define:
Minimum score
Required objectives
Maximum collisions
Completion required

Example:
{
  "passCriteria": {
    "mustComplete": true,
    "minimumScore": 90,
    "maximumCollisions": 0
  }
}

Then each run gets:
TEST PASS

or:
TEST FAIL

separate from its competition score.

28. Important distinction
These are different:
Competition result:
Score = 85

and:
Automated test result:
FAIL because minimum required = 90

Don't mix them.
