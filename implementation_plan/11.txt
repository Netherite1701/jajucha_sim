# Step 11 — Template Scene, Project Workflow, and User Scripts

This step turns the completed simulator systems into a clean, repeatable project workflow.

The goal is to provide:

* one authoritative simulator scene
* one clean template course
* one standard runtime hierarchy
* clear student/user script locations
* example scripts using the real-compatible `jchm` API
* launch and test scripts
* validation scripts
* build scripts
* documentation explaining the complete workflow

The resulting project should be usable without manually assembling Unity objects or guessing which files to run.

---

## 11.1 Core principle

The project must have one clearly documented default workflow:

```text
Open simulator
    ↓
Load or create course
    ↓
Start Python program
    ↓
Run simulation
    ↓
View scoring/debug information
    ↓
Reset or batch test
```

A new user should not need to:

* construct a scene hierarchy manually
* connect subsystem references manually
* create cameras manually
* configure the bridge manually
* copy scripts into arbitrary folders
* edit Unity prefabs to begin testing
* open Unity Editor for normal simulator use

The standalone build should provide the complete normal workflow.

---

# 11.2 Authoritative template scene

Create one authoritative runtime scene:

```text
Assets/JajuchaSim/Scenes/JajuchaSimulator.unity
```

This is the primary simulator scene for:

* Unity Play Mode
* standalone builds
* runtime map editing
* normal driving
* scoring
* automated testing

Do not maintain several slightly different “main” scenes.

Small isolated test scenes may exist under:

```text
Assets/JajuchaSim/Scenes/Tests/
```

but they are not user-facing simulator scenes.

# 11.4 `ApplicationBootstrap`

Create one bootstrap component responsible for ordered startup.

Example order:

```text
1. Load application configuration
2. Initialize simulation kernel
3. Initialize save/load paths
4. Load default course
5. Generate tile-based course runtime
6. Spawn/reset Jajucha vehicle
7. Initialize sensors
8. Start Python bridge
9. Initialize scenario/scoring
10. Initialize runtime UI
11. Enter READY state
```

The bootstrap must detect initialization failures and show a readable runtime error.

Do not allow random `Awake()` and `Start()` ordering to define system initialization implicitly.

---

# 11.5 Bootstrap result

Use an explicit startup result:

```text
BootstrapResult
├─ Success
├─ FailedSystem
├─ ErrorCode
└─ Message
```

Example runtime error:

```text
Simulator startup failed

System:
CourseManager

Reason:
Default course file was not found.

Path:
Courses/template_course.json
```

Do not leave users with only a `NullReferenceException`.

# 11.9 Default application modes

The simulator should expose clear modes:

```text
Drive
Edit Map
Test
Batch Test
```

Mode switching must be explicit.

Use a state such as:

```text
ApplicationMode
├─ Drive
├─ MapEditor
├─ SingleTest
└─ BatchTest
```

Do not infer application mode from which UI panel happens to be visible.

---

# 11.10 Mode behavior

## Drive

* observer camera follows car
* bridge active
* scoring optional
* minimal HUD visible
* debug panels available

## Edit Map

* simulation paused
* vehicle propulsion stopped
* top/editor camera active
* tile grid visible
* map tools enabled
* sensor output may remain available for preview
* course modifications allowed

## Single Test

* course reset
* scoring active
* test result saved
* runtime panels visible

## Batch Test

* repeated reset/run cycle
* observer rendering optional
* sensor rendering active
* results automatically collected

# 11.12 Minimal user script

Create:

```text
python/user/main.py
```

with a small real-compatible example.

Example behavior:

```python
import time

import jchm


def main() -> None:
    try:
        while True:
            image = jchm.camera.get_image("center")

            # Replace this section with the user's own perception
            # and driving algorithm.
            left = 0
            right = 0
            speed = 3

            jchm.control.set_motor(left, right, speed)

            time.sleep(0.03)

    except KeyboardInterrupt:
        jchm.control.set_motor(0, 0, 0)


if __name__ == "__main__":
    main()
```

The exact implementation should include appropriate error handling and documentation.

It must not assume ANN or FSM architecture.

# 11.19 User script rules

Document these rules in:

```text
python/user/README.md
```

1. Real driving code should use `jchm`.
2. Simulator lifecycle/testing tools use `jchm_sim`.
3. Do not modify simulator internals to implement autonomous logic.
4. Always send `speed=0` on shutdown where practical.
5. Handle bridge disconnects safely.
6. Do not depend on simulator ground truth for normal autonomous driving.
7. The same user code should remain as real-compatible as possible.

# Final Step 11 Result

After Step 11, a normal user workflow should be:

```text
1. Run setup script once.
2. Launch Jajucha Simulator.
3. Load or edit a tile-based course.
4. Run python/user/main.py in another terminal.
5. Watch the Jajucha drive in the main viewport.
6. Inspect cameras, events, scoring, and bridge status.
7. Reset, test, or batch-run the same external controller.
8. Save courses and export results.
```

The Unity project should no longer feel like a collection of subsystems requiring manual assembly.

It should behave as one coherent, documented simulator product whose runtime workflow matches the real Jajucha programming model as closely as the manual and confirmed hardware information permit.
