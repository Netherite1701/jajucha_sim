Step 4 — Camera System + jchm.camera Compatibility
This step adds the first real perception input.
The manual confirms that the Jajucha has three cameras named:
left
center
right
with the center camera mainly used for lane recognition and the left/right cameras used for depth-related perception. The real API is:
jchm.camera.get_image("center")
jchm.camera.get_image("left")
jchm.camera.get_image("right")
and it returns images usable directly with OpenCV.  
자주차 매뉴얼.pdf
The manual also provides:
jchm.camera.get_depth()
for a grayscale depth image, where brighter pixels indicate nearer objects and darker pixels indicate farther objects.  
자주차 매뉴얼.pdf
For this step, though, I would split implementation into Step 4A RGB cameras and Step 4B depth, because RGB camera correctness should be established before building stereo/depth behavior.

This real-style code:
import jchm

And:

4.13 Camera timing is not simulation timing
Simulation might run at:
100 Hz
while cameras run at:
30 FPS
Therefore:
physics tick:
0.01 s

~0.0333 s
The sensor scheduler must support different rates.
4.14 General sensor scheduling rule
Do not capture an image every time Python calls get_image().
That would make sensor timing dependent on Python processing speed.
Instead:
Camera sensor generates frames
at its configured frame rate

Python get_image()
returns most recent completed frame
This more closely represents real hardware.
4.15 Example frame schedule

Don't force camera generation onto every exact integer simulation tick.
Use an accumulator/schedule.

4.18 Color format contract
Unity commonly gives RGB ordering.
OpenCV convention is:
BGR
The manual shows camera frames being passed directly into OpenCV processing.  
자주차 매뉴얼.pdf
Therefore define Python-visible contract as:
uint8
height × width × 3
BGR
Convert exactly once.
Do not accidentally convert:
RGB → BGR → RGB → BGR
across layers.
4.19 Preferred conversion point
I would keep Unity output as:
RGB24
and mark protocol metadata:
format = RGB24
Then Python simulator backend converts:
RGB → BGR
before returning the NumPy array.
Why?
Because:
Unity naturally generates RGB.
Python/OpenCV naturally wants BGR.
conversion on Python side is straightforward and testable.
4.20 Vertical flipping
Unity render textures frequently use image-origin conventions that differ from NumPy/OpenCV expectations.
Therefore explicitly test:
top of world appears at top of returned image
Do not blindly add:
texture.Apply();
and assume orientation.
If needed:
flip vertically exactly once
before returning the Python frame.

4.22 Frame transport
Step 3 used newline-delimited JSON.
That is fine for commands.
It is not ideal for raw images.
Don't do:
{
  "image":"base64base64base64..."
}
for every frame.
That creates:
base64 overhead
large allocations
parsing overhead
unnecessary CPU usage
4.23 Extend protocol with binary payload framing
Use:
JSON header
+
binary payload
For example:
{"type":"response","id":21,"ok":true,"payload_type":"image","width":640,"height":480,"format":"rgb24","length":921600}
then exactly:
921600 binary bytes
because:
640 × 480 × 3 = 921600
4.24 Protocol framing must be unambiguous
The connection reader must know:
read header line
parse length
read EXACTLY length bytes
then next header
Never search for newline characters inside image bytes.
4.25 Control and image requests on one connection?
For Step 4, one persistent TCP connection can still work.
But serialization must be thread-safe:
one writer lock
so:
response header
binary frame
cannot be interrupted by another response.
Later, if throughput demands it, we can separate control and sensor channels.
Don't add that complexity yet.

Three cameras at:

30 FPS

~82.9 MB/s

4.57 Avoid PNG/JPEG for internal raw frame API initially
Compression saves bandwidth but adds:
encoding latency
decoding latency
loss
For localhost at modest resolution, raw RGB24 is simpler and more deterministic.
So baseline:

over the binary payload.
Later add compressed mode if needed.
4.58 Memory reuse
Do not allocate:
Texture2D
byte[]
from scratch 30 times per second per camera forever.
Use reusable buffers where Unity allows.
Architecture should aim toward:
persistent RenderTexture
persistent readback buffer

This prevents GC spikes.

Initial implementation can use a straightforward readback.
But prefer designing for:

If supported reliably in the Unity version we're using:

     ↓

     ↓

4.60 Important async rule
If async readback completes later, frame metadata must refer to capture time, not completion time.

4.61 Dropped frame behavior
If GPU readback can't keep up:
do not build an infinite queue
For a realtime camera, newer data is generally more useful.
Use bounded in-flight captures.
For baseline:
max 1 in-flight capture per camera
If next capture comes before previous one completes:
skip sensor capture
and increment:

4.63 Step 4B — Depth API
Once RGB is stable, implement:
jchm.camera.get_depth()
The manual describes the JCHM depth output as a grayscale image where:
near → brighter
far  → darker
and says the returned image is a NumPy array whose pixel brightness can be indexed to estimate proximity.  
자주차 매뉴얼.pdf
This is not necessarily a metric float depth map.
That distinction is important.
4.64 We need two depth representations internally
I recommend:
true metric simulator depth
         ↓
JCHM-compatible grayscale mapping
Internally:
distance in centimeters/meters
Then:
jchm.camera.get_depth()
returns the JCHM-style grayscale image.
Simulator-only tooling can later expose metric depth.
4.65 Why keep metric depth internally
Because later we may need:
debugging
ground truth
ANN labels
obstacle tests
simulation scoring
Metric depth is extremely valuable.
But exposing it via:
jchm.camera.get_depth()
would change the real API semantics.
So separate them.

4.68 Stereo versus direct renderer depth
The real platform derives depth using left/right camera information conceptually. The manual notes that stereo disparity could be used, while jchm directly provides a prepared depth image.  
자주차 매뉴얼.pdf
For simulation, I would not run OpenCV stereo reconstruction just to create errors.
Instead:

        ↓
metric depth
        ↓
JCHM grayscale transform
This gives clean ground truth.
Later we can optionally add a noisy stereo-emulation mode.
