Step 3 — Python Bridge + jchm Compatibility Layer
Step 3 connects the clean Unity vehicle from Step 2 to Python.
The goal is:
import jchm

jchm.control.set_motor(-5, -5, 3)

to control the Unity vehicle without changing student code semantics.
No camera yet. No ANN yet. No FSM yet. This step is only the control bridge.

3.1 Step 3 end state
At the end:
Python
  │
  │ jchm.control.set_motor(-5,-5,3)
  ▼
jchm simulator backend
  │
  │ localhost IPC
  ▼
Unity Bridge
  │
  ▼
JajuchaVehicle.SetMotor(-5,-5,3)
  │
  ▼
Vehicle Physics

And:
jchm.control.set_motor(0, 0, 0)

must stop propulsion while preserving the requested steering values exactly as defined in Step 2.

3.2 Main architectural rule
The bridge must not understand vehicle physics.
It only translates messages.
Bad:
PythonBridge
├─ computes steering angles
├─ computes motor velocity
├─ applies Rigidbody forces
└─ knows suspension

Good:
PythonBridge
    ↓
JajuchaVehicle.SetMotor(left,right,speed)

Everything physical remains in Vehicle.

3.4 Transport choice
For this simulator, I recommend:
TCP over localhost

initially.
Why not HTTP?
Because later camera frames and realtime control become much easier with a persistent socket.
Why not WebSocket immediately?
Possible, but unnecessary complexity.
Why not named pipes?
They are nice locally, but TCP is much easier to keep cross-platform.
So use:
127.0.0.1

with a configurable port.
Example:
8765


3.5 Never expose simulator publicly by default
Bind to:
127.0.0.1

not:
0.0.0.0

The bridge is for local development.
Later remote/container mode can explicitly enable another interface.

3.6 Bridge configuration
Create:
JajuchaBridgeConfig.asset

Fields:
Host                127.0.0.1
Port                8765

AutoStart           true

CommandTimeoutMs    1000

MaxMessageBytes     65536

ProtocolVersion     1

Keep network config separate from simulation config.

3.7 Protocol format
Use simple newline-delimited JSON.
Example:
{"type":"set_motor","left":-5,"right":-5,"speed":3}

followed by:
\n

Response:
{"type":"ack","ok":true}

This is easy to:
inspect manually
log
generate in Python
parse in Unity
test
Do not invent a binary protocol yet.

3.8 Every message needs a version
Prefer a handshake.
Python connects:
{
  "type": "hello",
  "protocol": 1,
  "client": "jchm-sim"
}

Unity responds:
{
  "type": "hello_ack",
  "protocol": 1,
  "simulator": "JajuchaSim"
}

If protocol versions don't match:
{
  "type": "error",
  "code": "PROTOCOL_VERSION_MISMATCH"
}

This avoids silent breakage later.

3.9 Message envelope
Do not make every command an unrelated JSON structure.
Use a consistent envelope:
{
  "type": "command",
  "id": 17,
  "name": "set_motor",
  "payload": {
    "left": -5,
    "right": -5,
    "speed": 3
  }
}

Response:
{
  "type": "response",
  "id": 17,
  "ok": true
}

The id lets Python match replies to requests.
This becomes more important once camera/status requests exist.

3.10 Keep transport and protocol separate
Structure:
TCP bytes
   ↓
BridgeConnection
   ↓
JSON line
   ↓
BridgeProtocol
   ↓
BridgeMessage
   ↓
CommandDispatcher
   ↓
JajuchaVehicle

Do not put socket reads, JSON parsing, and car commands into one 700-line class.

3.11 Threading model
TCP reading should not block the Unity main thread.
Use:
background receive thread/task

for socket I/O.
But never mutate Unity objects from that thread.
Instead:
network thread
     ↓
thread-safe incoming queue
     ↓
Unity simulation/main thread
     ↓
CommandDispatcher
     ↓
JajuchaVehicle

This is critical.

3.12 Command queue
Create:
ConcurrentQueue<BridgeMessage>

Conceptually:
Python sends command
      ↓
network receives
      ↓
IncomingCommands.Enqueue(...)
      ↓
simulation tick
      ↓
dequeue
      ↓
ApplyCommand()

This avoids race conditions.

3.13 Apply commands at simulation boundaries
Do not apply steering/motor commands at arbitrary render times.
At each simulation tick:
1. consume pending bridge commands
2. update current JCHM command
3. run vehicle simulation

This makes command timing deterministic.

3.14 Latest-command semantics
For motor control, if Python sends:
tick between updates:

set_motor(0,0,2)
set_motor(0,0,3)
set_motor(0,0,5)

before the next simulation tick, I recommend:
latest command wins

So only:
(0,0,5)

is applied.
Otherwise old commands can queue up and introduce artificial lag.

3.15 But preserve command order for non-motor commands later
So don't globally collapse all messages.
Implement command-specific policy:
set_motor
→ latest-wins

future reset
→ ordered

future capture_frame
→ ordered/request-response


3.16 Watchdog timeout
This is essential.
If Python dies while the car command is:
speed = 10

the simulated car should not drive forever.
Maintain:
LastMotorCommandReceiveTime

If:
now - lastCommand > timeout

then:
speed = 0

while preserving steering:
left = current left
right = current right
speed = 0

That matches the Step 2 invariant.

3.17 Timeout should use wall time, not simulation time
If simulation is paused:
SimulationTime

stops.
But Python may disconnect.
So watchdog should use:
real/unscaled wall time

not simulation clock time.

3.19 Disconnect behavior
On disconnect:
speed → 0

immediately or within one simulation tick.
Keep steering position unchanged.
Then wait for reconnection.
Do not crash Unity.

3.20 Multiple clients
For v1:
Allow exactly one control client.
If another connects:
{
  "type":"error",
  "code":"CLIENT_ALREADY_CONNECTED"
}

Multiple control clients are dangerous and unnecessary.
Later debug clients can be treated separately.

3.23 Backend abstraction
Inside Python:

          ↓
selected backend
     ┌────┴────┐
     ↓         ↓
real backend   simulator backend

For simulator development:

could select Unity.
Or a local configuration file.
Do not make students modify their autonomous algorithm.

3.24 Python control function
Conceptually:
def set_motor(left: int, right: int, speed: int):
    _backend.set_motor(left, right, speed)

Simulator backend:
def set_motor(left, right, speed):
    client.send_command(
        "set_motor",
        {
            "left": left,
            "right": right,
            "speed": speed,
        },
    )

Keep the public function tiny.

3.25 Range handling location
Do range validation in both places.
Python:
validate/clamp early

Unity:
validate/clamp again

Never trust the network boundary.
Canonical limits stay:
left/right: -10..10
speed:      -30..30


3.26 Simulator-specific API must be separate
Do not pollute:
jchm.control

with things that don't exist on the actual car.
Bad:
jchm.control.teleport_car()
jchm.control.set_simulation_speed()

Instead create:
jchm_sim

for simulator-only tooling.
Example:
import jchm
import jchm_sim

jchm.control.set_motor(0, 0, 3)

jchm_sim.reset()

That keeps real/sim compatibility clean.

3.29 Fail clearly if simulator isn't running
Bad:
ConnectionRefusedError: [WinError 10061]

Better:

Expected simulator at:
127.0.0.1:8765

Wrap lower-level socket errors.

3.30 Reconnection
If Unity restarts:
Python client
→ detects broken connection
→ reconnects on next command

Do not require restarting VS Code/Python unnecessarily.
Initial policy:
one reconnect attempt on next API call

Keep it simple.

3.31 Request timeout
Each synchronous request should have a timeout.
Example:
1 second

If Unity doesn't acknowledge:
JchmSimulatorTimeout

Never hang forever.

3.32 set_motor response policy
For normal use, the public function can be synchronous enough to ensure the command was accepted:
jchm.control.set_motor(...)

returns after Unity sends:
{"ok":true}

That makes errors deterministic.
Later, if latency matters, we can add a fire-and-forget optimization.
For local control, acknowledgement overhead is negligible.

3.40 Never send stack traces to students by default

3.41 JSON serialization
Use one serialization method consistently.
Do not mix:

Newtonsoft
custom regex parsing

If Unity's available JSON implementation handles the message model cleanly, use it.
Otherwise use Unity's supported Newtonsoft package.
Keep protocol DTOs simple so serialization is boring.

3.63 Bridge performance target
Motor control messages are tiny.
Target localhost round trip:
well below one simulation frame

At 100 Hz:
one tick = 10 ms

Ideally command round trip is:
< 5 ms

on the same computer.
But correctness matters more than optimizing microseconds in Step 3.

3.64 Avoid coupling Python timing to network latency
Later control code may do:
while True:
    ...
    jchm.control.set_motor(...)

We don't want every synchronous acknowledgement to dominate the loop.
So internally, plan for an eventual:
persistent socket

with lightweight request handling.
Do not reconnect per command.
That would be terrible.

3.65 Connection lifetime
This:
for _ in range(1000):
    jchm.control.set_motor(...)

should use:
one TCP connection

not 1000 connections.
Backend maintains a singleton/session connection internally.

3.66 Thread safety on Python side
Even if students don't initially use threads, make the backend safe enough that two Python threads don't interleave raw JSON bytes.
Use:
send lock
request ID lock

around request operations.

3.67 No camera over this design yet
Step 4 will need high-bandwidth data.
Do not prematurely cram images into the same simplistic request/response JSON encoding.
We can reuse the connection architecture but define a proper binary frame payload or separate stream.
For Step 3:
JSON control only

is enough.
